# Замер Агента-Маршрутизатора: результаты и принятые решения

Прогон `core/scripts/router-eval.mjs` на 21 случае (5 теоретических вопросов,
7 задач, 5 неполных запросов, 4 вне скоупа). Обе модели — на RX 6700 XT,
`format` = JSON Schema, размышление отключено, температура 0.

`v1` — системный промпт из [спецификации](./crypto-orchestrator-spec.md) §2
дословно. `v2` — он же плюс явное правило про границу
`TASK_REQUEST` / `CLARIFICATION_NEEDED`.

| | 1.7b v1 | 1.7b v2 | 8b v1 | **8b v2** |
|---|---|---|---|---|
| Валидный JSON | 100% | 100% | 100% | 100% |
| Интент строго | 81% | **90%** | 81% | 86% |
| Интент мягко | 86% | 90% | 86% | **95%** |
| THEORY_QUESTION | 5/5 | 5/5 | 5/5 | 5/5 |
| TASK_REQUEST (строго) | 3/7 | 6/7 | 5/7 | 5/7 |
| CLARIFICATION_NEEDED | 5/5 | 4/5 | 3/5 | 4/5 |
| OUT_OF_SCOPE | 4/4 | 4/4 | 4/4 | 4/4 |
| Медиана ответа | 1056 мс | 1136 мс | 2112 мс | 2291 мс |

Строгий счёт требует ровно ту категорию, что задана в наборе. Мягкий
допускает `OUT_OF_SCOPE` там, где по спецификации отказ выдаёт Планировщик
(«Купи мне 1 BTC», «Собери твиты Илона Маска»): пользователь получает отказ в
обоих случаях, просто более коротким путём.

## Что из этого следует

**JSON Schema обязательна, и её достаточно.** 84 запроса из 84 вернули
разбираемый JSON с интентом из перечисления. Схема ограничивает генерацию
грамматикой, поэтому структурно неверный ответ невозможен, а не маловероятен;
повтор при невалидном JSON в боевом коде не нужен.

**Температура 0 для маршрутизатора и планировщика.** Первые замеры шли при
сэмплировании по умолчанию, и один перевернувшийся случай сдвигает счёт на пять
пунктов — на таком наборе это неотличимо от разницы между промптами. В бою
важнее другое: один и тот же вопрос пользователя не должен попадать то в одну
ветку, то в другую. Для генерации текста ответа ноль, наоборот, вреден, поэтому
температура задаётся при вызове, а не в конфиге.

**Границу между категориями задавать правилом, а не примерами.** На `v1` пять
ошибок из шести у обеих моделей легли на одну границу — `TASK_REQUEST` против
`CLARIFICATION_NEEDED`, причём в противоположные стороны: 1.7b уводила задачу с
названным тикером в уточнение, 8b тащила запрос без тикера в задачу. Остальные
пары категорий не путались вообще. Спецификация разделяет эти два интента
примерами, и модель подгоняла запрос под ближайший пример вместо применения
критерия — увеличение модели ошибку не убирало, а переносило. Одна фраза о том,
что границу определяет наличие названного актива, подняла обе модели.

**Модель — `qwen3:8b`.** Строго 1.7b набрала больше (19 против 18), но оба
промаха 8b — те самые «допустимые», где отказ просто приходит раньше. По
содержательным ошибкам счёт обратный: у 8b одна («Какая сейчас цена?» ушло в
задачу, хотя актив не назван — это подхватит Планировщик, вернув
`canExecute: false`), у 1.7b две, и одна из них хуже по последствиям
(«Посмотри стакан по SOLUSDT» — символ указан полностью, а пользователь
получает встречный вопрос). Вдобавок 8b единственная разобрала «Сравни их за
неделю». Разница во времени в асинхронном конвейере несущественна, а на
Планировщике и теоретических ответах — тех самых задачах, которых этот замер
не касается, — преимущество 8B заметно больше.

## Границы этого замера

- **21 случай, написанный вручную.** Достаточно, чтобы увидеть систематическую
  ошибку, мало для тонкой настройки. Дальнейшая правка промпта под единственный
  оставшийся промах была бы подгонкой под шум — к промпту стоит вернуться на
  настоящих сообщениях пользователей.
- **Одно сообщение без истории.** По спецификации маршрутизатор видит последние
  3–5 реплик. Случай «Сравни их за неделю» без контекста неразрешим в принципе,
  и работу с историей надо мерить отдельным набором из цепочек сообщений.
- **Меряется только маршрутизатор.** Планировщик с вложенным JSON и качество
  теоретических ответов — открытые вопросы; выбор модели сделан в том числе в
  расчёте на них.
