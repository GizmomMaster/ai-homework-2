# Мониторинг токенов и три оптимизации: результаты

Мониторинг (`core/src/telemetry`), три оптимизации и инструменты замера
(`core/scripts/measure-context-savings.mjs`, `core/scripts/token-benchmark.mjs`)
реализованы и покрыты тестами (`npm test` — 448 тестов, все зелёные). Числа
ниже разделены на два рода намеренно.

## Как читать эти числа

* **Измеренные** — посчитаны реальным кодом (`truncateForClassifier`,
  `dedupeStepValues`, `estimateExchangeTokens`) на фиксированных фикстурах,
  сравнение «до» получено вызовом той же функции с параметром, отключающим
  оптимизацию (`maxChars: Infinity` и т.п.), — то есть один и тот же код
  считает обе стороны, а не два похожих замера в разное время. Сеть и модель
  для этого не нужны, число воспроизводимо командой из этого документа.
* **Расчётные** — где для числа нужен реальный вызов модели (сколько токенов
  бонсай-27b в среднем тратит на поле `reasoning`), а живой LM Studio/Ollama
  из среды, в которой писался код, не виден: там указана только верхняя
  оценка и как её проверить самостоятельно.

Всё это — не подмена реального прогона, а его нижняя граница: `--cache`
провайдера здесь тоже не работает по той же причине (см. `core/CLAUDE.md`,
раздел «Отступления от формулировки задания» в плане реализации), поэтому
входные токены таблиц ниже — это ровно то, что уйдёт по сети при каждом
вызове.

## Оптимизация 1 — обрезка истории для Router/Planner

`node scripts/measure-context-savings.mjs` (фикстура: два обмена, два
«отчёта» реалистичной длины — 414 и 399 знаков, как у настоящего ответа
SummaryAgent):

| | до | после | экономия |
|---|---|---|---|
| Router (история) | 300 токенов | 231 токен | −69 (−23%) |
| Planner (история) | 300 токенов | 231 токен | −69 (−23%) |
| **Итого за одно TASK_REQUEST-задание** | **600** | **462** | **−138 (−23%)** |

История передаётся Router и Planner дважды за одно задание с одним и тем же
содержимым — итоговая экономия задания вдвое больше, чем у одного вызова.
Эффект растёт с длиной истории: чем длиннее прошлые отчёты (у реального
`bonsai-27b` они часто длиннее фикстуры), тем больше экономия — 300 символов
`maxChars` обрезают почти любой многоабзацный отчёт до одной трети.

## Оптимизация 2 — дедуп пересекающихся полей инструментов

`get_crypto_current_price` и `get_crypto_24h_ticker_stats` по одному символу
пересекаются на 4 поля из 7-8 (цена, суточное изменение, максимум, минимум),
но называют их по-разному (`price`/`lastPrice`,
`priceChangePercent24h`/`priceChangePercent`, `high24h`/`high`,
`low24h`/`low`) — без учёта этого сравнение по имени поля не находит ничего
(этот факт нашёлся именно при первом прогоне замера — см. коммит с
исправлением на алиасы полей):

| | до | после | экономия |
|---|---|---|---|
| Данные двух шагов | 140 токенов | 113 токенов | −27 (−19%) |

Дедуп применяется, только когда планировщик действительно вызвал оба
инструмента по одному символу в одном плане — не на каждое задание.

## Оптимизация 3 — убраны неиспользуемые поля схемы маршрутизатора

**Расчётная**, не измеренная: экономит completion-токены, для которых нужен
живой вызов модели. `reasoning` и `outOfScopeReason` убраны из `ROUTER_SCHEMA`
и промпта — оба поля не читает ни `DialogService`, ни адаптер (проверено
`grep` по `core/src` и `telegram-bot/src`, тест-регрессия —
`routerAgent.test.js`: «не просит модель генерировать поля, которые никто не
читает»). Промпт просил «краткое обоснование выбора категории» — по
формулировке это полноценное предложение; при обычной для локальных моделей
скорости генерации разумная verbose-оценка — 15–40 токенов на каждый вызов
маршрутизатора, `outOfScopeReason` дешевле и не на каждом вызове (`null` для
трёх интентов из четырёх). Проверить на реальных числах:

```
node scripts/router-eval.mjs --verbose
```

и сравнить `completionTokens` в выводе с тем же прогоном на коммите до этой
оптимизации.

## Как получить числа с реальной моделью

Этот документ писался в среде без доступа к LM Studio/Ollama пользователя —
`curl http://localhost:1234/v1/models` и `:11434/api/tags` недоступны оттуда,
поэтому `latency_ms`, `estimated_cost_usd` и completion-токены (в т.ч. для
оптимизации 3) в нём не приведены как измеренные. Получить их у себя:

```bash
cd core
# «до»: на коммите перед тремя оптимизациями
git checkout <коммит-до> -- src/agents/RouterAgent.js src/agents/PlannerAgent.js src/agents/SummaryAgent.js src/domain/classifierContext.js
node scripts/token-benchmark.mjs --label=до > ../docs/_before.txt
git checkout HEAD -- .
# «после»: на текущем коммите
node scripts/token-benchmark.mjs --label=после > ../docs/_after.txt

node scripts/router-eval.mjs   # точность классификации не должна упасть
node scripts/task-eval.mjs     # точность плана не должна упасть
npm test                        # 448 тестов, включая новые для всех трёх оптимизаций
```

`token-benchmark.mjs` прогоняет 6 сессий (9 заданий, включая два многоходовых)
через полный конвейер `DialogService` с настоящей биржей и печатает то же,
что показывает дашборд: входные/выходные/reasoning/repeated-токены по
агентам, вызовы инструментов, условную стоимость и среднюю задержку. Впишите
оба прогона в таблицу ниже.

| | до | после |
|---|---|---|
| Input токенов, всего | _вписать_ | _вписать_ |
| Output токенов, всего | _вписать_ | _вписать_ |
| Repeated (повторный контекст) | _вписать_ | _вписать_ |
| Reasoning токенов | _вписать_ | _вписать_ |
| Условная стоимость | _вписать_ | _вписать_ |
| router-eval.mjs, точность | _вписать_ | _вписать_ (не хуже) |
| task-eval.mjs, точность | _вписать_ | _вписать_ (не хуже) |

## Качество: как проверялось без живой модели

Каждая оптимизация — с юнит-тестом, проверяющим её механику напрямую (а не
только «стало короче»):

* **Оптимизация 1** — `classifierContext.test.js` (обрезка), плюс
  `routerAgent.test.js`/`planner.test.js`: текущий вопрос никогда не
  обрезается, обрезается только прошлое.
* **Оптимизация 2** — `summary.test.js`: `dedupeStepValues` ловит пересечение
  между `get_crypto_current_price` и `get_crypto_24h_ticker_stats`, никогда не
  трогает `symbol`, не путает разные монеты и не удаляет поле, если значения
  разошлись.
* **Оптимизация 3** — `routerAgent.test.js`: убранные поля отсутствуют и в
  схеме, и в тексте промпта; `isRouterVerdict`/`DialogService` их и раньше не
  читали, регрессии в существующих тестах (`dialogService.test.js`) нет.

Настоящая проверка «не ухудшилось ли качество на модели» — `router-eval.mjs`
и `task-eval.mjs` из раздела выше: оба уже существовали до этой задачи и
измеряют именно то, что могли задеть оптимизации 1 и 3 (историю видит
классификатор, а не только план).
