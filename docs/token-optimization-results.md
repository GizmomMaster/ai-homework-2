# Мониторинг токенов и три оптимизации: результаты

Мониторинг (`core/src/telemetry`), три оптимизации и инструменты замера
(`core/scripts/measure-context-savings.mjs`, `core/scripts/token-benchmark.mjs`)
реализованы и покрыты тестами (`npm test` — 479 тестов в core и 163 в адаптере, все зелёные). Числа
ниже разделены на два рода намеренно.

## Как читать эти числа

* **Измеренные** — посчитаны реальным кодом (`truncateForClassifier`,
  `dedupeStepValues`, `estimateExchangeTokens`) на фиксированных фикстурах,
  сравнение «до» получено вызовом той же функции с параметром, отключающим
  оптимизацию (`maxChars: Infinity` и т.п.), — то есть один и тот же код
  считает обе стороны, а не два похожих замера в разное время. Сеть и модель
  для этого не нужны, число воспроизводимо командой из этого документа.
* **Расчётные** — где для числа нужен реальный вызов модели (сколько токенов
  бонсай-27b в среднем тратит на поле `reasoning`), а живой LM Studio/Ollama
  из среды, в которой писался код, не виден: там указана только верхняя
  оценка и как её проверить самостоятельно.

Всё это — не подмена реального прогона, а его нижняя граница: `--cache`
провайдера здесь тоже не работает по той же причине (см. `core/CLAUDE.md`,
раздел «Отступления от формулировки задания» в плане реализации), поэтому
входные токены таблиц ниже — это ровно то, что уйдёт по сети при каждом
вызове.

## Оптимизация 1 — обрезка истории для Router/Planner

`node scripts/measure-context-savings.mjs` (фикстура: два обмена, два
«отчёта» реалистичной длины — 414 и 399 знаков, как у настоящего ответа
SummaryAgent):

| | до | после | экономия |
|---|---|---|---|
| Router (история) | 300 токенов | 231 токен | −69 (−23%) |
| Planner (история) | 300 токенов | 231 токен | −69 (−23%) |
| **Итого за одно TASK_REQUEST-задание** | **600** | **462** | **−138 (−23%)** |

История передаётся Router и Planner дважды за одно задание с одним и тем же
содержимым — итоговая экономия задания вдвое больше, чем у одного вызова.
Эффект растёт с длиной истории: чем длиннее прошлые отчёты (у реального
`bonsai-27b` они часто длиннее фикстуры), тем больше экономия — 300 символов
`maxChars` обрезают почти любой многоабзацный отчёт до одной трети.

## Оптимизация 2 — дедуп пересекающихся полей инструментов

`get_crypto_current_price` и `get_crypto_24h_ticker_stats` по одному символу
пересекаются на 4 поля из 7-8 (цена, суточное изменение, максимум, минимум),
но называют их по-разному (`price`/`lastPrice`,
`priceChangePercent24h`/`priceChangePercent`, `high24h`/`high`,
`low24h`/`low`) — без учёта этого сравнение по имени поля не находит ничего
(этот факт нашёлся именно при первом прогоне замера — см. коммит с
исправлением на алиасы полей):

| | до | после | экономия |
|---|---|---|---|
| Данные двух шагов | 140 токенов | 113 токенов | −27 (−19%) |

Дедуп применяется, только когда планировщик действительно вызвал оба
инструмента по одному символу в одном плане — не на каждое задание.

## Оптимизация 3 — убраны неиспользуемые поля схемы маршрутизатора

**Расчётная**, не измеренная: экономит completion-токены, для которых нужен
живой вызов модели. `reasoning` и `outOfScopeReason` убраны из `ROUTER_SCHEMA`
и промпта — оба поля не читает ни `DialogService`, ни адаптер (проверено
`grep` по `core/src` и `telegram-bot/src`, тест-регрессия —
`routerAgent.test.js`: «не просит модель генерировать поля, которые никто не
читает»). Промпт просил «краткое обоснование выбора категории» — по
формулировке это полноценное предложение; при обычной для локальных моделей
скорости генерации разумная verbose-оценка — 15–40 токенов на каждый вызов
маршрутизатора, `outOfScopeReason` дешевле и не на каждом вызове (`null` для
трёх интентов из четырёх). Проверить на реальных числах:

```
node scripts/router-eval.mjs --verbose
```

и сравнить `completionTokens` в выводе с тем же прогоном на коммите до этой
оптимизации.

## Замер на реальной модели

Порядок работы у бенчмарка один: **снять базу на текущей реализации → внести
правки → перезамерить на том же наборе запросов**. Набор поэтому зафиксирован
в `SESSIONS` и снабжён отпечатком (`setHash`), который печатается в шапке и
кладётся в JSON: `--compare` сверяет его и предупреждает, если сравнивают
разные наборы. Правка `SESSIONS` меняет числа сильнее любой оптимизации, и
приписать себе эту разницу — самая лёгкая ошибка такого замера.

```bash
# 1. База: текущая реализация, как есть
docker compose exec core node scripts/token-benchmark.mjs \
    --label=база --runs=3 --json=/app/data/base.json

# 2. …правки в промптах, схемах, обрезке контекста…
docker compose up -d --build core        # скрипт исполняется из образа

# 3. Повторный замер тем же набором, сразу с разницей
docker compose exec core node scripts/token-benchmark.mjs \
    --label=после-правок --runs=3 --compare=/app/data/base.json
```

`/app/data` — это `./core/data` на хосте (общий volume), поэтому файл базы
переживёт пересборку образа и будет доступен обоим прогонам.

Этот документ писался в среде без доступа к LM Studio/Ollama пользователя —
`curl http://localhost:1234/v1/models` и `:11434/api/tags` недоступны оттуда,
поэтому измеренные `latency_ms`, `estimated_cost_usd` и completion-токены в
нём не приведены.

### Если проект развёрнут в Docker (обычный случай)

Скрипты лежат внутри образа Core (`COPY scripts ./scripts`), там же —
`node_modules` и Python с TA-Lib. Ставить что-либо на хост не нужно, всё
запускается в работающем контейнере:

```bash
docker compose up -d                                  # Core должен быть запущен
docker compose exec core node scripts/token-benchmark.mjs --label=после --runs=3
```

**Адрес модели.** Внутри контейнера `localhost` — это сам контейнер, а не
машина с LM Studio. В `core/.env` должно стоять
`LMSTUDIO_BASE_URL=http://host.docker.internal:1234` (для Ollama —
`OLLAMA_BASE_URL=http://host.docker.internal:11434`); `docker-compose.yml`
это имя уже пробрасывает через `extra_hosts`. Если адрес неверный, бенчмарк
не станет молча выдавать нули — он прервётся на первом же задании и скажет,
куда не достучался.

**Про пересборку.** Скрипт исполняется из образа, поэтому любая правка на
хосте до него не доедет, пока не выполнен `docker compose up -d --build core`.
Без этого второй прогон повторит первый один в один, и разница выйдет нулевой
по причине, не имеющей отношения к правкам.

Если нужно сравниться не с текущей реализацией, а с прошлым коммитом, набор
запросов должен приехать из **сегодняшнего** дерева, иначе отпечатки не
совпадут и сравнение будет бессмысленным:

```bash
git checkout <коммит-до> -- core/src/agents core/src/domain/classifierContext.js
git checkout HEAD -- core/scripts/token-benchmark.mjs   # набор запросов — текущий
docker compose up -d --build core
docker compose exec core node scripts/token-benchmark.mjs --label=до --runs=3 --json=/app/data/base.json
git checkout HEAD -- core && docker compose up -d --build core
```

Проверки качества — там же:

```bash
docker compose exec core node scripts/router-eval.mjs   # точность классификации не должна упасть
docker compose exec core node scripts/task-eval.mjs     # точность плана не должна упасть
```

Тесты образ не содержит (в него едут только `src`, `scripts` и `skills`),
поэтому `npm test` запускается на хосте из `core/` и `telegram-bot/` — модель
и сеть для них не нужны.

### Без Docker

```bash
cd core
npm install                                     # better-sqlite3 собирается из исходников
node scripts/token-benchmark.mjs --label=после --runs=3
```

### Какие метрики снимаются

Все, что пишет телеметрия, — по колонкам обеих таблиц, без пропусков:

| | что показывается |
|---|---|
| Задания | всего, по статусам, по веткам маршрутизатора; вызовов модели и инструментов, input, output и стоимость **на одно задание** |
| Модель (`llm_calls`) | вызовов всего и неудачных с разбивкой по `error_code`; input, output, reasoning, repeated (и его доля от input); условная стоимость; задержка средняя и максимальная |
| Инструменты (`tool_calls`) | вызовов всего и неудачных с разбивкой по `error_code`; вход и выход в байтах; оценка вывода в токенах; длительность средняя и максимальная |
| По агентам | вызовы, отказы, input, output, reasoning, repeated, стоимость, средняя задержка |
| По стадиям | вызовы и токены (`stage` — отдельная колонка, с `agent_id` совпадает не всегда) |
| По инструментам | вызовы, отказы, выход в байтах и токенах, средняя длительность |

Строки «на задание» — то, по чему сравнивают: с `--runs>1` суммы растут
вместе с числом прогонов, а средние нет.

### Что именно прогоняется

`token-benchmark.mjs` — 12 сессий, 15 заданий за прогон, через полный
конвейер `DialogService` с настоящей биржей. Набор покрывает все четыре ветки
маршрутизатора, все семь инструментов реестра, отказ инструмента
(`unsupported_asset` на RSI по DOGE) и два многоходовых диалога — без
последних не измерить оптимизацию 1, она работает именно на накопленной
истории. Печатает то же, что показывает дашборд: входные, выходные,
reasoning- и repeated-токены по агентам, вызовы инструментов, условную
стоимость и среднюю задержку, плюс средние на одно задание.

`--runs=3` берётся не для солидности: температура у отвечающих агентов не
нулевая, длина их ответов гуляет между прогонами и в многоходовых сессиях
утягивает за собой input-токены следующих ходов. Сравнивать «до» и «после»
имеет смысл по строке «На задание» при одинаковом `--runs`.

Первая строка вывода — состав реестра инструментов. Он влияет на длину
промпта планировщика, а `get_crypto_rsi` попадает в реестр не на всякой
машине (нужен Python с TA-Lib), поэтому у двух прогонов эта строка должна
совпадать — иначе числа несопоставимы.

Впишите оба прогона в таблицу ниже.

| | до | после |
|---|---|---|
| Input токенов, всего | _вписать_ | _вписать_ |
| Output токенов, всего | _вписать_ | _вписать_ |
| Repeated (повторный контекст) | _вписать_ | _вписать_ |
| Reasoning токенов | _вписать_ | _вписать_ |
| Условная стоимость | _вписать_ | _вписать_ |
| router-eval.mjs, точность | _вписать_ | _вписать_ (не хуже) |
| task-eval.mjs, точность | _вписать_ | _вписать_ (не хуже) |

## Качество: как проверялось без живой модели

Каждая оптимизация — с юнит-тестом, проверяющим её механику напрямую (а не
только «стало короче»):

* **Оптимизация 1** — `classifierContext.test.js` (обрезка), плюс
  `routerAgent.test.js`/`planner.test.js`: текущий вопрос никогда не
  обрезается, обрезается только прошлое.
* **Оптимизация 2** — `summary.test.js`: `dedupeStepValues` ловит пересечение
  между `get_crypto_current_price` и `get_crypto_24h_ticker_stats`, никогда не
  трогает `symbol`, не путает разные монеты и не удаляет поле, если значения
  разошлись.
* **Оптимизация 3** — `routerAgent.test.js`: убранные поля отсутствуют и в
  схеме, и в тексте промпта; `isRouterVerdict`/`DialogService` их и раньше не
  читали, регрессии в существующих тестах (`dialogService.test.js`) нет.

Настоящая проверка «не ухудшилось ли качество на модели» — `router-eval.mjs`
и `task-eval.mjs` из раздела выше: оба уже существовали до этой задачи и
измеряют именно то, что могли задеть оптимизации 1 и 3 (историю видит
классификатор, а не только план).
