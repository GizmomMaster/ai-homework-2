# CLAUDE.md

## Repository state

Telegram-бот на Node.js с интеграцией Ollama реализован в `telegram-bot/`. Исходное ТЗ — `telegram-bot/promt.md`, подробная спецификация — `telegram-bot/SPEC.md`, инструкция по запуску — `telegram-bot/README.md`.

Идёт выделение сервиса `core/` (Core Orchestrator): доменная логика — сессии, контекст, учёт токенов, вызов LLM — переезжает туда, а `telegram-bot/` становится тонким адаптером Telegram ↔ HTTP. Обмен асинхронный: адаптер шлёт `POST /v1/conversations/:adapter/:externalId/messages` и получает `202 { jobId }`, готовый ответ Core доставляет обратно запросом на `POST /callbacks/replies` адаптера. На тот же callback-адрес, по мере обработки задания, Core шлёт ещё и промежуточный статус (`status: "progress"`, поле `progress.stage` из `PROGRESS_STAGE` в `core/src/domain/DialogService.js`) — необязательные, недоставляемые повторно события через `core/src/jobs/ProgressNotifier.js`; в отличие от финального ответа они не участвуют в очереди доставки с ретраями и не дедуплицируются по `jobId` (`telegram-bot/src/http/callbackServer.js`). Адаптер показывает их пользователю одним редактируемым статусным сообщением (`telegram-bot/src/handlers/progressHandler.js`), которое удаляется перед отправкой финального ответа. План реализации: https://claude.ai/code/artifact/c7d79508-b02c-415f-96ce-47422f9dcbda

Сервисы подтверждают друг друга общим секретом `CORE_AUTH_TOKEN`, запускаются вместе через корневой `docker-compose.yml`.  Перенос старой базы бота выполняется скриптом `core/scripts/migrate-from-adapter.mjs`.

Следующее направление — `docs/crypto-orchestrator-spec.md`: превращение Core в мультиагентного ассистента для криптотрейдеров (маршрутизатор интентов, планировщик задач, инструменты поверх публичных API бирж). Все пять фаз плана выполнены: маршрутизатор интентов (`core/src/agents/`) разводит запрос по четырём веткам; теоретические вопросы отвечает `TheoryAgent` со своим промптом и температурой, задачи пока отклоняются с причиной `task_unsupported` — сбор данных подключается в фазе 4. Агенты строятся на двух каркасах: `JsonAgent` (схема, температура 0) для разбора запроса и `TextAgent` для ответа пользователю. Слой инструментов `core/src/tools/` — читающие инструменты поверх публичных API с валидацией параметров, кешем и контрактом отказа: пять поверх Binance плюс `get_crypto_market_overview` поверх CoinGecko (`CoinGeckoClient.js`, `marketOverview.js`). Второй источник нужен по существу, а не для подстраховки: капитализации у биржи нет, а часть монет верхушки рейтинга на Binance не листится — для них дневные точки CoinGecko служат откатом. Инструмент появляется в реестре только при заданном `COINGECKO_BASE_URL`.

Команда `/start` в боте показывает сводку по рынку: топ-10 по капитализации без стейблкоинов и обёрток, итоги прошедших суток UTC (открытие, закрытие, изменение, объём) и текущее состояние. Отдаётся синхронным `GET /v1/market/overview` вместо очереди заданий: состав ответа задан командой, поэтому ни маршрутизатор, ни планировщик не нужны — модель вызывается один раз. Связывает всё `core/src/domain/MarketOverviewService.js`.

**Работа поделена: таблицы собирает код (`renderMarketOverview.js`), текст пишет модель (`MarketOverviewAgent`).** Деление далось опытом. Сначала всю сводку писала модель, и `bonsai-27b` раз за разом промахивалась мимо формата — то ставила markdown-таблицу, то клала в блок кода заголовок и фразу вместо таблицы; каждый промах стоил всей сводки, включая правильный вывод о рынке. Теперь ломаться нечему: выравнивание держится на подсчёте пробелов, а это работа для кода; увидеть в цифрах картину — работа для модели. Отказ модели стоит одного абзаца, а не всей сводки, за которую уже заплачено запросами к двум внешним API. Комментарий проверяется `unusableCommentary` — требований мало, потому что испортить абзац текста можно только перестав быть абзацем текста.

Числа приходят модели **уже отформатированными** (`buildBrief`): переокруглив, она разошлась бы с цифрами в таблице под собственным текстом, и расхождение было бы видно пользователю.

Причина, по которой таблицы вообще уходят блоками кода: **Telegram не поддерживает таблицы ни в markdown, ни в HTML**. Колонки держатся только на моноширинном `<pre>`, в который `telegram-bot/src/telegram/markdown.js` превращает ```-блок. По той же причине тикеры с подчёркиванием (`FIGR_HELOC`) вне блоков берутся в инлайн-код — иначе `_` рвёт разметку курсива.

Итоги прошедших суток кешируются отдельно от текущих цен и до конца дня (дата в ключе заменяет инвалидацию): свеча закрыта и не изменится, а перезапрашивалась вместе с ценами каждую минуту. Неудачи при этом не кешируются — `TtlCache.through` не запоминает `undefined`, иначе одно оборванное соединение закрепило бы `н/д` на сутки. Фазы 4–5 подключили его к конвейеру: `PlannerAgent` строит план (схема и промпт собираются из реестра инструментов), `PlanExecutor` выполняет шаги параллельно, `SummaryAgent` сводит отчёт; `renderReport.js` остался откатом на случай отказа сводящего агента. Замеры: `scripts/router-eval.mjs` для маршрутизатора, `scripts/task-eval.mjs` для планировщика — второй проверяет параметры настоящими валидаторами, не обращаясь к бирже. Промпт маршрутизатора живёт в `RouterAgent.js` и импортируется скриптом замера `core/scripts/router-eval.mjs` — результаты и вытекающие из них решения в `docs/router-eval-results.md`. План реализации по фазам: https://claude.ai/code/artifact/1411862d-990e-4163-9ec4-7efb4ad88f7a

Целевая локальная модель — `bonsai-27b` через LM Studio (`LLM_PROVIDER=lmstudio`) на видеокарте (RX 6700 XT, 12 ГБ). `LmStudioRunner` говорит с встроенным HTTP-сервером LM Studio (OpenAI-совместимый API `/v1/chat/completions`), а не с Ollama, поэтому формат запроса другой: температура — поле верхнего уровня, JSON Schema уходит через `response_format`, счётчики токенов берутся из `usage.*`. У LM Studio нет запросного аналога `num_ctx` — длину контекста задают один раз при загрузке модели в самом приложении (не меньше `CONTEXT_WINDOW_TOKENS`), иначе LM Studio молча обрежет историю раньше нашего лимита. Блок размышления `<think>…</think>` (на случай, если модель окажется reasoning-моделью) `stripThinking()` вырезает независимо от раннера — у OpenAI-совместимого API LM Studio нет стандартизованного поля-переключателя вроде Ollama-шного `think`. Ollama (`qwen3:8b`) остаётся доступна как альтернативный провайдер (`LLM_PROVIDER=ollama`) — `OllamaRunner` и связанные с ним `OLLAMA_THINK`/расчёт KV-кеша не удалены, детали в комментариях `core/.env.example`.
