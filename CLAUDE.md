# CLAUDE.md

## Repository state

Telegram-бот на Node.js с интеграцией Ollama реализован в `telegram-bot/`. Исходное ТЗ — `telegram-bot/promt.md`, подробная спецификация — `telegram-bot/SPEC.md`, инструкция по запуску — `telegram-bot/README.md`.

Идёт выделение сервиса `core/` (Core Orchestrator): доменная логика — сессии, контекст, учёт токенов, вызов LLM — переезжает туда, а `telegram-bot/` становится тонким адаптером Telegram ↔ HTTP. Обмен асинхронный: адаптер шлёт `POST /v1/conversations/:adapter/:externalId/messages` и получает `202 { jobId }`, готовый ответ Core доставляет обратно запросом на `POST /callbacks/replies` адаптера. На тот же callback-адрес, по мере обработки задания, Core шлёт ещё и промежуточный статус (`status: "progress"`, поле `progress.stage` из `PROGRESS_STAGE` в `core/src/domain/DialogService.js`) — необязательные, недоставляемые повторно события через `core/src/jobs/ProgressNotifier.js`; в отличие от финального ответа они не участвуют в очереди доставки с ретраями и не дедуплицируются по `jobId` (`telegram-bot/src/http/callbackServer.js`). Порядок их доставки поэтому не гарантирован, и `JobRunner` нумерует события задания (`progress.seq`), а адаптер выстраивает их в цепочку по `jobId` и отбрасывает устаревшие: без номера запоздавшее «разбираю запрос» затирало уже показанное «свожу отчёт», а два одновременных первых события заводили два статусных сообщения, из которых убиралось одно. Адаптер показывает их пользователю одним редактируемым статусным сообщением (`telegram-bot/src/handlers/progressHandler.js`), которое удаляется перед отправкой финального ответа; `finish()` при этом дожидается уже начатых событий, иначе то из них, что прошло проверку до отметки о завершении, заводило сообщение после его удаления. План реализации: https://claude.ai/code/artifact/c7d79508-b02c-415f-96ce-47422f9dcbda

**Задание никогда не остаётся в `running`.** Очередь берёт только `queued`, поэтому застрявшее задание не переспросит никто, доставки не будет, и пользователь досмотрит застывшее статусное сообщение до перезапуска Core. `JobRunner` ловит вокруг `dialogService.process()` и непредвиденные исключения — те, что не разобрал сам `DialogService`, — и завершает задание отказом `internal_error`. Возврат `running → queued` при старте (`requeueStale`) остаётся только для настоящего падения процесса.

Сервисы подтверждают друг друга общим секретом `CORE_AUTH_TOKEN` (сравнение — `timingSafeEqual` по обе стороны), запускаются вместе через корневой `docker-compose.yml`.  Перенос старой базы бота выполняется скриптом `core/scripts/migrate-from-adapter.mjs`.

`telegram-bot` и `dashboard` работают в контейнере от пользователя `node`, **а `core` намеренно остаётся под root**: он пишет в `/app/data`, а это bind-mount каталога `./core/data` с хоста, и uid, зашитый в образ, обязан совпасть с владельцем каталога на конкретной машине. `chown` в образе тут бесполезен — монтирование его перекрывает. Правильно закрывается либо `user:` в compose под uid хозяина, либо переездом на именованный volume; и то и другое — решение о том, где живут данные, а не правка Dockerfile.

Следующее направление — `docs/crypto-orchestrator-spec.md`: превращение Core в мультиагентного ассистента для криптотрейдеров (маршрутизатор интентов, планировщик задач, инструменты поверх публичных API бирж). Все пять фаз плана выполнены: маршрутизатор интентов (`core/src/agents/`) разводит запрос по четырём веткам; теоретические вопросы отвечает `TheoryAgent` со своим промптом и температурой, задачи пока отклоняются с причиной `task_unsupported` — сбор данных подключается в фазе 4. Агенты строятся на двух каркасах: `JsonAgent` (схема, температура 0) для разбора запроса и `TextAgent` для ответа пользователю. Слой инструментов `core/src/tools/` — читающие инструменты поверх публичных API с валидацией параметров, кешем и контрактом отказа: пять поверх Binance плюс `get_crypto_market_overview` поверх CoinGecko (`CoinGeckoClient.js`, `marketOverview.js`). Второй источник нужен по существу, а не для подстраховки: капитализации у биржи нет, а часть монет верхушки рейтинга на Binance не листится — для них дневные точки CoinGecko служат откатом. Инструмент появляется в реестре только при заданном `COINGECKO_BASE_URL`.

Оба клиента наследуют `PublicApiClient.js` — там сборка запроса, таймаут, разбор отказов сети и проверка, что тело вообще JSON. Через этот класс проходят два правила, разъезжаться которым между источниками нельзя: базовый адрес берётся из конфига и никогда из параметров вызова (их формирует модель, и адрес среди них означал бы, что её вывод решает, к какому хосту идёт сервис), а путь складывается только из констант нашего кода. У наследников остаётся своё: коды ответа источника и **род его названия** в сообщениях — «Binance ответила», но «CoinGecko ответил», поэтому глаголы передаются в конструктор, а не выводятся из имени.

Команда `/start` в боте показывает сводку по рынку: топ-10 по капитализации без стейблкоинов и обёрток, итоги прошедших суток UTC (открытие, закрытие, изменение, объём) и текущее состояние. Отдаётся синхронным `GET /v1/market/overview` вместо очереди заданий: состав ответа задан командой, поэтому ни маршрутизатор, ни планировщик не нужны — модель вызывается один раз. Связывает всё `core/src/domain/MarketOverviewService.js`.

**Работа поделена: таблицы собирает код (`renderMarketOverview.js`), текст пишет модель (`MarketOverviewAgent`).** Деление далось опытом. Сначала всю сводку писала модель, и `bonsai-27b` раз за разом промахивалась мимо формата — то ставила markdown-таблицу, то клала в блок кода заголовок и фразу вместо таблицы; каждый промах стоил всей сводки, включая правильный вывод о рынке. Теперь ломаться нечему: выравнивание держится на подсчёте пробелов, а это работа для кода; увидеть в цифрах картину — работа для модели. Отказ модели стоит одного абзаца, а не всей сводки, за которую уже заплачено запросами к двум внешним API. Комментарий проверяется `unusableCommentary` — требований мало, потому что испортить абзац текста можно только перестав быть абзацем текста.

Числа приходят модели **уже отформатированными** (`buildBrief`): переокруглив, она разошлась бы с цифрами в таблице под собственным текстом, и расхождение было бы видно пользователю.

Причина, по которой таблицы вообще уходят блоками кода: **Telegram не поддерживает таблицы ни в markdown, ни в HTML**. Колонки держатся только на моноширинном `<pre>`, в который `telegram-bot/src/telegram/markdown.js` превращает ```-блок. По той же причине тикеры с подчёркиванием (`FIGR_HELOC`) вне блоков берутся в инлайн-код — иначе `_` рвёт разметку курсива.

Откат на CoinGecko срабатывает по двум разным причинам, и различать их обязательно: пары **нет в листинге** (свойство монеты, до полуночи не изменится) либо **биржа не ответила** (сегодняшняя заминка). `collectHistory` это знает — `NOT_LISTED` против `null`, — и передаёт дальше полем `binanceMiss`, снаружи кеша: причина относится к попытке, а не к итогам суток, которые кеш и хранит. Сводка разводит их по двум сноскам; пока сноска была одна, она приписывала монете отсутствие пары каждый раз, когда до Binance просто не достучались.

Итоги прошедших суток кешируются отдельно от текущих цен и до конца дня (дата в ключе заменяет инвалидацию): свеча закрыта и не изменится, а перезапрашивалась вместе с ценами каждую минуту. Неудачи при этом не кешируются — `TtlCache.through` не запоминает `undefined`, иначе одно оборванное соединение закрепило бы `н/д` на сутки. **В записи кеша лежит промис, а не готовое значение**: шаги плана идут параллельно (`CONCURRENCY` в `PlanExecutor`), и пока запись появлялась только после `await`, два шага по одной паре успевали оба промахнуться мимо кеша и сходить на биржу порознь — то есть ровно в том случае, ради которого кеш и заводился (квота Binance считается на адрес). Срок жизни отсчитывается от начала вычисления, а не от конца; отказ и `undefined` из кеша убираются, но только если запись всё ещё своя — за время ожидания её мог вытеснить `#evict`. Фазы 4–5 подключили его к конвейеру: `PlannerAgent` строит план (схема и промпт собираются из реестра инструментов), `PlanExecutor` выполняет шаги параллельно, `SummaryAgent` сводит отчёт; `renderReport.js` остался откатом на случай отказа сводящего агента. Замеры: `scripts/router-eval.mjs` для маршрутизатора, `scripts/task-eval.mjs` для планировщика — второй проверяет параметры настоящими валидаторами, не обращаясь к бирже. Промпт маршрутизатора живёт в `RouterAgent.js` и импортируется скриптом замера `core/scripts/router-eval.mjs` — результаты и вытекающие из них решения в `docs/router-eval-results.md`. План реализации по фазам: https://claude.ai/code/artifact/1411862d-990e-4163-9ec4-7efb4ad88f7a

Показатель RSI считает Python-скрипт `core/scripts/rsi/rsi.py` поверх **TA-Lib**, а не наш код: сглаживание Уайлдера рекурсивно, и своя реализация стала бы третьей версией правды рядом с терминалом пользователя и графиком биржи. TA-Lib выбрана из двух разрешённых ТЗ библиотек по двум причинам: под musl (Alpine, на котором собран образ Core) у `pandas_ta` нет колёс — он тянет numba, — а его RSI засевает сглаживание первым приращением вместо среднего и на коротком ряде расходится с классическим на 16 пунктов при шкале 0..100. Свечи скрипту передаются через stdin, а сеть ему запрещена флагом `--no-fetch`: HTTP-клиент биржи с кешем и разбором её кодов у Core уже есть, второй такой же в подпроцессе означал бы вторую политику ретраев. Сам скрипт ходить на биржу умеет — но только когда его запускают руками. Инструмент `get_crypto_rsi` появляется в реестре, только если при старте нашёлся интерпретатор с TA-Lib (`core/src/tools/pythonBin.js`: `python3` из PATH, затем `core/.venv`, затем `~/.venv`; кандидат проверяется импортом библиотеки, а не наличием файла), по той же логике, что и CoinGecko: инструмент, отказывающий на каждом вызове уже после того, как планировщик потратил на него шаг, хуже отсутствующего. Настройка — флаг `RSI_ENABLED` (по умолчанию `true`), а не путь: путь разный на каждой машине, и один и тот же `core/.env` читают и хост, и контейнер (compose пробрасывает его через `env_file`, перекрывая `ENV` образа — поэтому в Dockerfile venv добавлен в `PATH`, а не прописан переменной). `RSI_PYTHON_BIN` остался запасным выходом для conda/pyenv: если он задан, поиск не выполняется вовсе.

**Поддерживаются только BTC и ETH.** Ограничение продублировано в трёх местах намеренно: в скрипте (он самостоятельная утилита, и запуск руками не должен его обходить), в инструменте (отказ не должен стоить ни свечей, ни подпроцесса) и в навыке — чтобы отказ приходил от планировщика словами, а не кодом. По той же логике продублирован и список интервалов свечей, но за ним следит тест: он вычитывает `INTERVALS` прямо из `rsi.py` и сравнивает с `KLINE_INTERVALS`. Списки уже расходились — в скрипте не было `1s`, планировщик мог его выбрать беспрепятственно, и отказ приходил после похода за свечами и запуска подпроцесса, да ещё словами «не удалось выполнить расчёт» вместо «такого интервала нет».

Отсюда же новые коды `unsupported_asset` и `computation_failed`: прежние говорят про биржу («биржа ответила ошибкой», «не удалось связаться с биржей»), а здесь биржа отвечает исправно — ограничение наше, и объяснять его нужно иначе. Когда не удался ни один шаг плана, `DialogService` отдаёт код первого шага, поэтому до адаптера доходит **любой** код `TOOL_ERROR`, и у каждого свой текст (`FAILURE_TEXTS` в `replyHandler.js`): пользователю важно отличать «я назвал монету, которой нет» от «биржа временно молчит» — в первом случае помогает он сам, во втором только ожидание. Запасной текст про модель не говорит: она в этих отказах ни при чём. `buildBrief` теперь отдаёт модели ещё и текст отказа шага: «RSI считается только для BTC и ETH» — это то, что пользователь должен прочитать, а без причины модель пишет размытое «данные получить не удалось».

**Навыки** (`core/skills/*/SKILL.md`, загрузчик `core/src/skills/index.js`) — слой поверх реестра инструментов. Реестр отвечает на вопрос «что система умеет» и даёт схему плана; навык — на вопрос «когда это уместно и что ответить, если просят невозможное». Тело файла дословно дописывается в конец промпта планировщика: правила — это промпт, их подбирают и правят, и править их должно быть можно, не трогая JavaScript. Раздела нет вовсе, когда навыков нет: пустой заголовок небольшую модель отвлекает.

Целевая локальная модель — `bonsai-27b` через LM Studio (`LLM_PROVIDER=lmstudio`) на видеокарте (RX 6700 XT, 12 ГБ). `LmStudioRunner` говорит с встроенным HTTP-сервером LM Studio (OpenAI-совместимый API `/v1/chat/completions`), а не с Ollama, поэтому формат запроса другой: температура — поле верхнего уровня, JSON Schema уходит через `response_format`, счётчики токенов берутся из `usage.*`. У LM Studio нет запросного аналога `num_ctx` — длину контекста задают один раз при загрузке модели в самом приложении (не меньше `CONTEXT_WINDOW_TOKENS`), иначе LM Studio молча обрежет историю раньше нашего лимита. Блок размышления `<think>…</think>` (на случай, если модель окажется reasoning-моделью) `stripThinking()` вырезает независимо от раннера — у OpenAI-совместимого API LM Studio нет стандартизованного поля-переключателя вроде Ollama-шного `think`. Ollama (`qwen3:8b`) остаётся доступна как альтернативный провайдер (`LLM_PROVIDER=ollama`) — `OllamaRunner` и связанные с ним `OLLAMA_THINK`/расчёт KV-кеша не удалены, детали в комментариях `core/.env.example`.

Слой `core/src/telemetry/` пишет одну строку в `llm_calls` на каждый вызов `LlmRunner.chat()` и одну в `tool_calls` на каждый `executeTool()` из `PlanExecutor` — оба узких места уже существовали, менять их контракт не пришлось. Декоратор `InstrumentedLlmRunner` оборачивает раннер по одному разу на агента при сборке в `app.js`; `job_id` и монотонный `turn_number` доступны декоратору и `PlanExecutor` не через параметры конструктора (это сломало бы DI во всех тестах, где агенты собираются с фейковыми раннерами напрямую), а через `AsyncLocalStorage` (`core/src/telemetry/context.js`), которую открывает `JobRunner` вокруг `dialogService.process()` — модуль работает без инициализации на месте вызова, как `core/src/logger.js`, и молчит, пока `initTelemetry(db)` не вызван явно. Синглтон при этом — только точка входа, но **не место хранения**: подготовленные запросы и цены лежат в `WeakMap` по базам, а нужная база едет в том же контексте задания. Приложений в одном процессе может оказаться несколько (так поднимаются тесты), и пока связка была одна на модуль, записи всех уходили в базу последнего `initTelemetry` — молча, строки писались, просто не туда. Вызовам вне задания (обзор рынка для `/start`, скрипты замера) выбирать не из чего, для них по-прежнему главный последний `initTelemetry`. Ни Ollama, ни LM Studio не отдают `cached_tokens`: вместо выдумывания числа `markSeen()` сравнивает текст каждого отправленного сообщения с уже отправленными в рамках того же задания — так поймалось, что Router и Planner получают один и тот же срез истории дважды за одно `TASK_REQUEST`. `reasoning_tokens` тоже не отдаётся отдельным полем ни у одного провайдера — `stripThinking()` в `core/src/llm/stripThinking.js` теперь возвращает вместе с очищенным текстом ещё и оценку длины вырезанного блока `<think>`. `estimated_cost_usd` считается по условной цене за 1M токенов (`TELEMETRY_PRICE_INPUT_PER_1M`/`_OUTPUT_PER_1M`) — модель локальная и в эксплуатации бесплатна, число показывает лишь ориентир для сопоставимого облачного API.

Три оптимизации, каждая на свой источник лишних токенов: (1) `truncateForClassifier` (`core/src/domain/classifierContext.js`) обрезает прошлые реплики истории, которые видят только Router и Planner, — текущий вопрос не трогает; (2) `dedupeStepValues` в `SummaryAgent.js` убирает из брифа сводящего агента поля, которые `get_crypto_current_price` и `get_crypto_24h_ticker_stats` показывают дважды под разными именами (`price`/`lastPrice`, `priceChangePercent24h`/`priceChangePercent`, `high24h`/`high`, `low24h`/`low` — Binance называет одно и то же по-разному в двух эндпоинтах, точное совпадение по имени поля эту пару не ловит вообще); (3) из `ROUTER_SCHEMA` убраны `reasoning` и `outOfScopeReason` — оба поля из спецификации, но ни одно не читает ни `DialogService`, ни адаптер, а каждое стоит модели токенов генерации на каждый вызов маршрутизатора. `core/scripts/measure-context-savings.mjs` меряет входные токены оптимизаций 1 и 2 точно и без сети (сравнивает один и тот же код с оптимизацией включённой и выключенной); оптимизация 3 экономит completion-токены, которые без живой модели не измерить, и `core/scripts/token-benchmark.mjs` — для этого: прогоняет фиксированный набор сессий через весь `DialogService` на настоящем LM Studio/Ollama и снимает **все** колонки обеих таблиц телеметрии — включая те, которых нет на дашборде: успешность вызовов, длительность инструментов и размеры их вывода в байтах. Порядок работы у него один: снять базу на текущей реализации, внести правки, перезамерить тем же набором (`--json` сохраняет замер, `--compare` печатает разницу). Поэтому **набор запросов `SESSIONS` менять нельзя мимоходом**: он снабжён отпечатком `setHash`, который `--compare` сверяет, — правка набора двигает числа сильнее любой оптимизации, и приписать эту разницу себе легче всего именно так. Реестр инструментов бенчмарк собирает ровно как `app.js`, включая RSI: иначе он мерил бы промпт планировщика, которого в эксплуатации не бывает. Числа и как их получить самостоятельно — `docs/token-optimization-results.md`.

Дашборд — отдельный сервис `dashboard/` (свой `package.json`, свой `Dockerfile`, третий сервис в `docker-compose.yml`), а не часть Core: открывает `core/data/core.db` в режиме `readonly: true` через общий volume, HTTP-контракта с Core ему для этого не нужно. Единственный сервис, чей порт публикуется наружу (`8090`) — его открывают в браузере, а не вызывают по HTTP-контракту. Публикуется **только на `127.0.0.1`**: проверки доступа у дашборда нет вовсе, а страница задания показывает `request_text` — то есть переписку пользователей; на `0.0.0.0` она была бы открыта всей локальной сети.
