# Telegram-бот с локальной LLM (Ollama)

Telegram-бот, который принимает текстовое сообщение и пересылает его в
локально запущенную LLM через Ollama, возвращая ответ модели обратно в чат.
История переписки в рамках диалога сохраняется в SQLite и передаётся модели
как контекст, чтобы поддерживать полноценный многоходовый диалог.

## Требования

- Node.js версии 18 или выше.
- Установленная и запущенная [Ollama](https://ollama.com).
- Скачанная модель для Ollama, например:

  ```bash
  ollama pull llama3
  ```

- Токен Telegram-бота, полученный у [@BotFather](https://t.me/BotFather).

## Установка

```bash
cd telegram-bot
npm install
```

(Единственная внешняя зависимость — `better-sqlite3` для хранения истории
переписки; для остального проект использует только встроенные модули Node.js.)

## Настройка

1. Скопируйте файл с примером конфигурации:

   ```bash
   cp .env.example .env
   ```

2. Откройте `.env` и заполните переменные:

   ```
   TELEGRAM_BOT_TOKEN=ваш_токен_от_BotFather
   LLM_PROVIDER=ollama
   MAX_MESSAGE_LENGTH=1000
   SQLITE_DB_PATH=./data/bot.db
   CONTEXT_WINDOW_TOKENS=50000
   OLLAMA_BASE_URL=http://localhost:11434
   OLLAMA_MODEL=llama3
   ```

   Как получить `TELEGRAM_BOT_TOKEN`:
   - Откройте чат с [@BotFather](https://t.me/BotFather) в Telegram.
   - Отправьте команду `/newbot` и следуйте инструкциям (укажите имя и username бота).
   - BotFather пришлёт токен вида `123456789:AAExxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx` — скопируйте его в `.env`.

   `OLLAMA_MODEL` должна совпадать с именем модели, которую вы скачали через `ollama pull`.

   `MAX_MESSAGE_LENGTH` — максимальная длина текстового сообщения в символах
   (по умолчанию 1000). Подробнее — в разделе «Ограничения».

   `SQLITE_DB_PATH` — путь к файлу базы данных SQLite, где хранится история
   переписки (по умолчанию `./data/bot.db` относительно рабочего каталога).
   Каталог создаётся автоматически при первом запуске.

   `CONTEXT_WINDOW_TOKENS` — размер контекстного окна диалога в токенах (по
   умолчанию 50000). Подробнее — в разделе «История переписки и контекст».

## История переписки и контекст

- **История хранится в SQLite.** Каждое сообщение пользователя и ответ модели
  сохраняются в файле, указанном в `SQLITE_DB_PATH`. При каждом новом
  сообщении боту передаётся вся история текущего диалога, поэтому модель
  помнит предыдущие реплики (полноценный многоходовый диалог, а не
  одноразовые запросы).
- **Диалоги (сессии).** В рамках одного Telegram-чата история накапливается в
  "сессии" диалога. Новая сессия создаётся автоматически при первом сообщении
  в чате.
- **Команда `/new`.** Начинает новую сессию диалога в этом чате — предыдущая
  история остаётся в базе данных, но больше не передаётся модели как
  контекст. Используйте её, если хотите начать разговор "с чистого листа".
- **Лимит контекстного окна.** Размер истории ограничен `CONTEXT_WINDOW_TOKENS`
  токенами (по умолчанию 50000; считается по фактическим данным токенайзера
  модели Ollama — сумма `prompt_eval_count` и `eval_count` из ответа модели).
  При достижении лимита бот присылает сообщение с просьбой начать новый
  диалог командой `/new` — до этого новые сообщения в переполненном диалоге
  не обрабатываются.
- **Контекст модели (`num_ctx`).** Бот явно передаёт Ollama параметр
  `options.num_ctx = CONTEXT_WINDOW_TOKENS`, чтобы у модели было ровно
  столько памяти под контекст, сколько мы отслеживаем. Без этого Ollama
  использует собственный контекст модели по умолчанию (часто заметно меньше
  `CONTEXT_WINDOW_TOKENS`) и молча обрезает старые сообщения истории, чтобы
  уместиться в него — тогда счётчик токенов в логах не растёт до
  настроенного лимита, а колеблется или уменьшается от диалога к диалогу.
  Учтите: большой `num_ctx` требует больше оперативной памяти/VRAM — если
  модель не тянет заданный `CONTEXT_WINDOW_TOKENS`, уменьшите значение в
  `.env`.

## Форматирование ответов модели

Ollama обычно отдаёт текст в Markdown (`**жирный**`, `*курсив*`, `` `код` ``,
блоки кода в тройных кавычках, ссылки `[текст](url)`, заголовки `#`). Перед
отправкой в Telegram бот конвертирует этот Markdown в HTML-подмножество,
которое Telegram умеет рендерить при `parse_mode=HTML`
(`src/telegram/markdown.js`) — сообщение приходит уже с настоящим жирным
шрифтом, курсивом, моноширинным кодом и кликабельными ссылками, а не с
«сырыми» звёздочками и решётками.

Если разметка в ответе модели окажется некорректной и Telegram откажется её
парсить, бот не теряет сообщение — автоматически повторяет отправку без
`parse_mode` (пользователь увидит текст как есть, без форматирования).

## Ограничения

- **Только текстовые сообщения.** Фото, документы, голосовые, стикеры и
  прочие вложения бот не обрабатывает. При получении такого сообщения он
  отвечает пользователю предупреждением, не обращаясь к LLM.
- **Лимит длины сообщения.** Сообщение длиннее `MAX_MESSAGE_LENGTH` символов
  (по умолчанию 1000) отклоняется с предупреждением — запрос к LLM не
  отправляется. Изменить лимит можно в `.env` (см. «Настройка»), без правок
  кода.

## Запуск

Убедитесь, что Ollama запущена (обычно она стартует автоматически после установки;
проверить можно командой `ollama list`), затем запустите бота:

```bash
npm start
```

При успешном старте в консоли появится:

```
Бот запущен, ожидание сообщений...
```

## Проверка работы

1. Найдите вашего бота в Telegram по username, указанному при создании через BotFather.
2. Отправьте любое текстовое сообщение.
3. Бот перешлёт его в Ollama и пришлёт ответ модели в чат.

## Возможные проблемы

- **«Отсутствует обязательная переменная окружения TELEGRAM_BOT_TOKEN»** —
  не заполнен `.env`. Проверьте, что файл `.env` существует и содержит токен
  (см. раздел «Настройка»).
- **«Не удалось подключиться к Ollama по адресу ...»** — Ollama не запущена
  или слушает другой адрес/порт. Проверьте, что `ollama serve` работает
  (или запущено desktop-приложение Ollama), и что `OLLAMA_BASE_URL` в `.env`
  указывает на правильный адрес.
- **Ollama отвечает ошибкой про модель** — модель, указанная в `OLLAMA_MODEL`,
  не скачана. Выполните `ollama pull <модель>`.
- **Бот не отвечает в Telegram** — проверьте, что `TELEGRAM_BOT_TOKEN`
  скопирован без лишних пробелов и что у процесса `npm start` есть доступ
  в интернет (для запросов к Telegram API).

## Запуск в Docker

Бот можно запустить в контейнере, при этом он продолжит получать сообщения
из Telegram (через long polling — исходящее соединение, входящий порт не
нужен) и обращаться к LLM, запущенной локально на хост-машине (Ollama,
LM Studio и т.п.).

### 1. Настройте `.env`

Как и при обычном запуске, скопируйте `.env.example` в `.env` и заполните
`TELEGRAM_BOT_TOKEN`. Ключевой момент — `OLLAMA_BASE_URL` должен указывать
не на `localhost` (это будет localhost *внутри контейнера*, а не хоста), а на
`host.docker.internal`:

```
OLLAMA_BASE_URL=http://host.docker.internal:11434
```

### 2. Разрешите Ollama слушать не только localhost

По умолчанию Ollama на хосте слушает `127.0.0.1:11434` и недоступна извне
контейнера. Запустите Ollama с `OLLAMA_HOST=0.0.0.0`:

```bash
OLLAMA_HOST=0.0.0.0 ollama serve
```

(если Ollama установлена как systemd-сервис — добавьте
`Environment="OLLAMA_HOST=0.0.0.0"` в юнит и перезапустите его).

### 3. Соберите и запустите контейнер

```bash
docker compose up --build -d
```

Файл `docker-compose.yml` уже содержит `extra_hosts: host.docker.internal:host-gateway`,
необходимый для того, чтобы имя `host.docker.internal` резолвилось в адрес
хоста на Linux (на Docker Desktop для Mac/Windows оно работает по умолчанию).

**Хранение истории переписки (SQLite) в Docker.** `docker-compose.yml` монтирует
каталог `./data` с хост-машины в `/app/data` внутри контейнера
(`volumes: ./data:/app/data`). Файл базы данных (`SQLITE_DB_PATH`, по
умолчанию `./data/bot.db`) при этом создаётся на хосте и переживает
пересоздание контейнера (`docker compose up --build`, обновление образа и
т.п.) — история переписки не теряется.

Логи бота:

```bash
docker compose logs -f
```

Остановить:

```bash
docker compose down
```

Без `docker compose` то же самое можно сделать через `docker build`/`docker run`
(не забудьте примонтировать том с данными SQLite через `-v`):

```bash
docker build -t telegram-local-llm-bot .
docker run -d --name telegram-bot \
  --env-file .env \
  --add-host=host.docker.internal:host-gateway \
  -v "$(pwd)/data:/app/data" \
  --restart unless-stopped \
  telegram-local-llm-bot
```

### Нюансы запуска на Windows (Docker Desktop)

Общая схема та же, но есть несколько мест, где Windows отличается от Linux/macOS:

- **`host.docker.internal` работает из коробки.** На Docker Desktop для Windows
  это имя резолвится в адрес хоста автоматически, поэтому строка `extra_hosts`
  в `docker-compose.yml` не мешает, но фактически не обязательна — можно не
  трогать.

- **Переменную `OLLAMA_HOST` нужно задавать по-другому.** Синтаксис
  `OLLAMA_HOST=0.0.0.0 ollama serve` — это bash, в Windows он не сработает.
  Если запускаете Ollama вручную из терминала:

  ```powershell
  # PowerShell
  $env:OLLAMA_HOST = "0.0.0.0"
  ollama serve
  ```

  ```cmd
  :: cmd.exe
  set OLLAMA_HOST=0.0.0.0
  ollama serve
  ```

  Но обычно на Windows Ollama работает как фоновое приложение (иконка в трее),
  а не через `ollama serve` в терминале. В этом случае так просто переменную
  не подставить — надо задать её как системную/пользовательскую переменную
  окружения (Панель управления → Система → Дополнительные параметры системы →
  Переменные среды → добавить `OLLAMA_HOST=0.0.0.0`), а затем **полностью
  перезапустить Ollama** (выйти из трея, запустить заново) — иначе
  приложение не подхватит новое значение.

- **Файрвол Windows может блокировать соединение.** Docker Desktop поднимает
  контейнеры в отдельной виртуальной сети (WSL2), и первое обращение к порту
  `11434` может быть заблокировано Брандмауэром Windows. Если после всех
  настроек бот всё равно не может достучаться до Ollama — проверьте, не
  просит ли Windows разрешить доступ (обычно всплывает диалог при первом
  запуске `ollama serve`/приложения), и при необходимости добавьте входящее
  правило для порта 11434 в Брандмауэре Windows.

- **Сохраняйте `.env` в кодировке UTF-8 без BOM.** Если создать/отредактировать
  `.env` через обычный Блокнот (Notepad), он может добавить BOM-байты в
  начало файла — тогда первая переменная (обычно `TELEGRAM_BOT_TOKEN`) не
  распознается. Используйте VS Code или другой редактор с явным выбором
  кодировки «UTF-8» (без BOM).

- **Команды запуска — те же.** `docker compose up --build -d`,
  `docker compose logs -f`, `docker compose down` выполняются одинаково что
  в PowerShell, что в cmd, что в WSL — сам Docker Desktop абстрагирует
  различия. Рекомендуется использовать бэкенд WSL2 (настройка по умолчанию
  в актуальных версиях Docker Desktop).

### Возможные проблемы при запуске в Docker

- **«Не удалось подключиться к Ollama»** — проверьте, что `OLLAMA_BASE_URL`
  в `.env` указывает на `host.docker.internal`, а не `localhost`, и что
  Ollama запущена с `OLLAMA_HOST=0.0.0.0` (см. шаг 2).
- **`host.docker.internal` не резолвится** — убедитесь, что в
  `docker-compose.yml` (или в `docker run`) присутствует
  `--add-host=host.docker.internal:host-gateway`; это требует Docker
  Engine ≥ 20.10.

## Расширение: добавление нового локального LLM-раннера

LLM-интеграции реализованы через единый интерфейс (`src/llm/LlmRunner.js`),
поэтому Ollama — не единственный возможный backend. Чтобы добавить новый
раннер (например, LM Studio):

1. Создайте `src/llm/<Provider>Runner.js` с классом, реализующим метод
   `chat(messages): Promise<{ content, promptTokens, completionTokens }>`,
   где `messages` — массив `{ role: "user"|"assistant", content }` (история
   диалога передаётся вызывающим кодом, раннер её не хранит). Поля
   `promptTokens`/`completionTokens` нужны для отслеживания контекстного
   окна — если провайдер не отдаёт статистику по токенам, можно вернуть
   грубую оценку (например, по длине текста).
2. Зарегистрируйте его в фабрике `src/llm/index.js` (добавьте ветку `switch`
   по значению `LLM_PROVIDER`).
3. Укажите `LLM_PROVIDER=<provider>` в `.env`.

Код `src/telegram/*` и `src/handlers/*` при этом менять не нужно.
