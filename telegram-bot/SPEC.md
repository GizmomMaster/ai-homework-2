# Спецификация: Telegram-бот с локальной LLM (Ollama)

Основано на требованиях из [`promt.md`](./promt.md).

## 1. Назначение

Telegram-бот, работающий на локальной машине пользователя (или в Docker).
Принимает текстовое сообщение, пересылает его как запрос в локально
запущенную LLM (через Ollama) вместе с историей текущего диалога, и
возвращает ответ модели пользователю в чат. История переписки сохраняется в
SQLite и используется как контекст для полноценного многоходового диалога —
см. п. 12.

## 2. Технологический стек

- **Язык/рантайм:** Node.js (JavaScript, без TypeScript).
- **Telegram Bot API:** только нативные HTTP-запросы (`fetch`/`https`), без
  сторонних библиотек (`node-telegram-bot-api`, `telegraf` и т.п. — под запретом).
- **Получение обновлений:** long polling через метод `getUpdates`
  (без вебхуков — упрощает локальный запуск без публичного HTTPS-адреса).
- **LLM backend:** Ollama HTTP API (`http://localhost:11434` по умолчанию),
  доступ через слой абстракции (см. п. 4).
- **Конфигурация:** `.env`-файл, загружаемый через `process.loadEnvFile()`
  (Node.js ≥ 20.6, без пакета `dotenv`) либо через `dotenv`, если версия Node
  ниже — решить на этапе реализации в зависимости от доступной версии Node.
- **Зависимости:** минимальные; в идеале — ноль npm-зависимостей, только
  встроенные модули Node.js.

## 4. Абстракция LLM-runner'а

Требование ТЗ — заложить возможность подключать другие локальные LLM-раннеры
(LM Studio, llama.cpp server, и т.д.), не переписывая логику бота.

### Контракт (`src/llm/LlmRunner.js`)

Каждый runner — объект/класс с единым асинхронным методом:

```js
/**
 * @typedef {Object} LlmRunner
 * @property {(messages: {role: "user"|"assistant", content: string}[]) => Promise<{
 *   content: string, promptTokens: number, completionTokens: number
 * }>} chat
 *   Отправляет историю сообщений сессии в LLM и возвращает текст ответа
 *   вместе со статистикой токенов. Сам раннер историю не хранит — её
 *   передаёт вызывающий код (messageHandler, через ChatRepository).
 */
```

### Реализация Ollama (`src/llm/OllamaRunner.js`)

- Использует эндпоинт `POST /api/chat` (а не `/api/generate`) — позволяет
  передать модели полную историю сообщений сессии одним запросом и получить
  честную статистику по токенам (`prompt_eval_count`, `eval_count`) в ответе.
- Параметры: `model` (из `.env`, например `OLLAMA_MODEL`), `stream: false`
  (без потоковой генерации — упрощает интеграцию с Telegram, где ответ
  отправляется одним сообщением).
- Базовый URL Ollama берётся из `.env` (`OLLAMA_BASE_URL`, по умолчанию
  `http://localhost:11434`).
- Ошибки сети / недоступности Ollama — пробрасываются наверх с понятным
  сообщением, чтобы `messageHandler` мог отправить пользователю
  человекочитаемую ошибку вместо падения процесса.

### Фабрика (`src/llm/index.js`)

- Читает `LLM_PROVIDER` из конфига (`ollama` по умолчанию).
- Возвращает соответствующий runner. Добавление нового провайдера в будущем —
  это новый файл `src/llm/<Provider>Runner.js` + одна ветка в фабрике, без
  изменений в `messageHandler` и `polling`.

## 5. Работа с Telegram Bot API (без сторонних библиотек)

### `src/telegram/client.js`

Минимальный клиент поверх `fetch`:

- `getUpdates({ offset, timeout })` → `GET/POST https://api.telegram.org/bot<TOKEN>/getUpdates`
  - Использовать long polling: `timeout` ~30 сек на стороне Telegram.
- `sendMessage({ chatId, text, parseMode? })` → `POST https://api.telegram.org/bot<TOKEN>/sendMessage`
  - Разбивать длинные ответы модели на части, если текст превышает лимит
    Telegram в 4096 символов на сообщение.
  - Если передан `parseMode` (используется `"HTML"`) — отправлять с
    `parse_mode`; если Telegram вернёт ошибку парсинга разметки, повторно
    отправить тот же текст без `parse_mode`, чтобы не терять сообщение
    (см. `markdown.js` ниже).
- `setMyCommands(commands)` → `POST https://api.telegram.org/bot<TOKEN>/setMyCommands`
  - Регистрирует список команд бота в меню Telegram (кнопка "/" рядом с
    полем ввода). Вызывается один раз при старте (`src/index.js`) со списком
    `[{ command: "new", description: "..." }]`. Ошибка регистрации
    логируется, но не останавливает запуск бота — сами команды всё равно
    обрабатываются в `polling.js` независимо от меню.

### `src/telegram/markdown.js`

- `markdownToTelegramHtml(markdown): string` — конвертирует Markdown, который
  обычно отдают LLM (`**жирный**`, `*курсив*`, `` `код` ``, блоки кода в
  тройных кавычках, `~~зачёркнутый~~`, `[текст](url)`, заголовки `#`), в
  HTML-подмножество, которое Telegram поддерживает при `parse_mode=HTML`
  (только теги `b`/`i`/`s`/`code`/`pre`/`a`).
- Заголовки превращаются в жирную строку (Telegram не поддерживает
  `<h1>`-`<h6>`); списки/цитаты не оформляются отдельными тегами (Telegram их
  не поддерживает в HTML-режиме) — как обычный текст с `-`/`>` они и так
  читаемы.
- Применяется только к ответу модели в `messageHandler.js` — собственные
  служебные сообщения бота (предупреждения, `/new`) остаются простым текстом.

### `src/telegram/polling.js`

- Бесконечный цикл: запрос `getUpdates` с `offset = last_update_id + 1`,
  обработка каждого текстового сообщения через `messageHandler`, обновление
  `offset`.
- Обработка ошибок сети — retry с небольшой задержкой, без падения процесса.
- Игнорировать не-текстовые сообщения (стикеры, фото и т.д.) — либо не
  отвечать, либо отвечать коротким пояснением («Я понимаю только текст»,
  решить при реализации — не критично для MVP).

## 6. Поток обработки сообщения (`src/handlers/messageHandler.js`)

1. Получено текстовое сообщение → `{ chatId, text }`.
2. `chatRepository.getOrCreateActiveSession(chatId)` — получить/создать
   текущую сессию диалога. Если `session.totalTokens` уже достиг
   `contextWindowTokens` — сообщение не обрабатывается, пользователю
   отправляется просьба выполнить `/new` (см. п. 12).
3. `chatRepository.addMessage(session.id, "user", text)`.
4. `chatRepository.getMessages(session.id)` → вся история сессии, вызов
   `llmRunner.chat(messages)`.
5. При успехе — сохранить ответ (`role: "assistant"`), обновить
   `total_tokens` сессии, отправить `telegramClient.sendMessage({ chatId,
   text: markdownToTelegramHtml(response.content), parseMode: "HTML" })`
   (см. п. 5, `markdown.js`). Если новый `total_tokens` достиг лимита —
   дополнительно отправить предупреждение про `/new`.
6. При ошибке (LLM недоступна, таймаут и т.п.) — отправить пользователю
   сообщение об ошибке, залогировать причину в консоль на сервере.

## 8. Обработка ошибок и логирование

- Все ошибки (сеть Telegram, сеть Ollama, некорректный ответ модели)
  логируются в `stdout/stderr` с достаточным контекстом (chatId, время,
  текст ошибки — но не сам токен бота).
- Бот не должен падать из-за единичной ошибки обработки одного сообщения —
  цикл polling продолжает работу.

## 12. История переписки и контекстное окно

Требование — вести полноценный диалог с LLM (а не одноразовые запросы),
сохраняя историю сообщений между вызовами.

### Хранилище (SQLite)

- Используется `better-sqlite3` (синхронный API, единственная внешняя
  npm-зависимость проекта). Путь к файлу БД — `SQLITE_DB_PATH` в `.env`
  (по умолчанию `./data/bot.db`); каталог создаётся автоматически
  (`src/db/database.js`).
- При запуске в Docker каталог с БД монтируется как volume
  (`./data:/app/data` в `docker-compose.yml`), чтобы файл переживал
  пересоздание контейнера.
- Схема (см. `src/db/database.js`):
  - `chat_sessions(id, chat_id, total_tokens, created_at)` — сессии диалога
    в рамках Telegram-чата (`chat_id`).
  - `chat_messages(id, session_id, role, content, created_at)` — сообщения
    сессии (`role`: `user`/`assistant`).
- `src/db/chatRepository.js` (`ChatRepository`) — единственная точка доступа
  к данным: получение/создание активной сессии, добавление сообщений, чтение
  истории, обновление счётчика токенов сессии.

### Модель сессий

- Активная сессия чата — последняя созданная сессия для данного `chat_id`
  (сортировка по `id`). Явного флага "активности" нет — достаточно порядка
  создания.
- Первое сообщение в чате создаёт новую сессию автоматически.
- Команда `/new` (с учётом возможного суффикса `/new@BotName` и регистра)
  создаёт новую сессию для чата, не удаляя предыдущую историю из БД —
  предыдущие сообщения просто перестают передаваться модели как контекст.

### Передача истории модели и подсчёт токенов

- `LlmRunner` (`src/llm/LlmRunner.js`) больше не работает в режиме
  "один prompt — один ответ": метод `chat(messages)` принимает полную
  историю сессии (`{ role, content }[]`) и возвращает
  `{ content, promptTokens, completionTokens }`.
- `OllamaRunner` реализует это через `POST /api/chat` (а не `/api/generate`),
  передавая туда весь массив сообщений. Ollama при `stream: false`
  возвращает в ответе `prompt_eval_count` и `eval_count` — это **фактическое**
  число токенов по токенайзеру используемой модели, а не приближённая оценка.
- После каждого обмена `messageHandler` сохраняет
  `total_tokens = promptTokens + completionTokens` для сессии — это и есть
  текущий размер контекстного окна, потребляемого моделью.
- `OllamaRunner` также передаёт `options.num_ctx = contextWindowTokens`
  (прокидывается из фабрики `src/llm/index.js` при создании раннера). Это
  необходимо: без явного `num_ctx` Ollama использует собственный дефолтный
  контекст модели (часто заметно меньше `CONTEXT_WINDOW_TOKENS`) и молча
  обрезает старые сообщения истории под него ещё до подсчёта токенов — в
  результате `prompt_eval_count` не растёт к настроенному лимиту, а
  колеблется/уменьшается от обмена к обмену. Совпадение `num_ctx` с
  `CONTEXT_WINDOW_TOKENS` гарантирует, что модель реально хранит именно то
  окно, которое отслеживает бот.

### Лимит контекстного окна

- Размер лимита задаётся `CONTEXT_WINDOW_TOKENS` в `.env` (по умолчанию
  `50000`), валидируется как положительное целое (см. `positiveInt` в
  `src/config.js`).
- Перед обращением к LLM `messageHandler` проверяет `total_tokens` активной
  сессии: если лимит уже достигнут — новое сообщение не сохраняется и не
  уходит в LLM, пользователю отправляется просьба выполнить `/new`.
- Если лимит достигнут по итогам текущего обмена (после ответа модели) —
  пользователю дополнительно отправляется предупреждающее сообщение о том,
  что контекст заполнен и нужно начать новый диалог через `/new`.
